THE SHIFT

从多开几个窗口碰结果，
到一条可校验的流水线。

从早期 AI 辅助字幕，到多模态自动化，再到 maijev。变化不只是换了模型，更在于：哪些事情交给模型，哪些不该让它猜。

早期探索2025 / VIDEO REFERENCE

跳过逐行原文校对，让模型先合并、纠错与翻译。

2025 年的方案已不只是“把日文翻成中文”：用 CapCut 生成带时间轴的字幕，按约 30 分钟手动切段，再交给 Gemini，结合预翻译分析与词库合并碎句、修正人名，最后由人校对中文并微调时间轴。目标是减少一次完整的日文原文校对，而不是取消人工校对。

多模态路线GRILLMASTER

不只读字幕，也让模型听音频、看画面。

GrillMaster 先用完整字幕、音频、代表帧与节目信息生成全片简报，再把简报、局部音视频和字幕分块交给模型翻译。它重视综艺语气、人物关系和画面语境，并提供结构校验、修复与后续交付环节。

本项目的选择MAIJEV

延续同一个思路，把不确定的操作收进程序边界。

过去需要多开窗口挑合并结果、复制完整 SRT、检查空行和时间码；现在把合并与翻译拆成独立任务，模型只返回分组或 id + 译文。程序校验结构、恢复时间轴，自动分批与缓存；预分析中的译名归并则成为可选的全片共享词库。

历史参考：《日语字幕一小时 300 行+？AI 字幕工作流新思路》↗（2025-08-31）。内容依据作者提供的 vCaptions 逐字稿整理。“300 行 / 小时”是作者当时的人工做档效率，不是模型生成速度，也不是本项目的性能指标。

WHAT CHANGED

早期的四个瓶颈，
现在分别处理。

以下是视频中描述的 2025 年使用体验，不是对今天 Whisper、CapCut 或其他字幕项目的统一评测。maijev 改变的是流程，不承诺消除所有误差。

时间点可用，句子却很碎

早期 CapCut 流程中，一个词或一句话可能被拆成多行，手工合并费时；让大模型合并，又会出现不同窗口合并程度不同的情况。

现在：从词级时间戳构造 atom，单独让模型决定合并分组，再检查结构和静音跨度。语义断句仍有不确定性，但可以单独调试，不和翻译混在一次输出里。

错的人名，会一路传进译文

早期方案用领域词库与预翻译分析，让模型结合上下文纠正名字，从而减少一次完整的原文校对。这个思路在 maijev 中被保留。

现在：用可选 OCR 实体、来源 cast 名单与全日文行生成共享词库，也允许人工覆盖。模型推断不等于事实核验，词库仍可能需要修正。

长段输出难稳定，需要多跑几次

视频中约 30 分钟是作者当时可接受的手动切段界限，仍会多开窗口比较合并结果；这不是所有模型固定的时长上限。

现在：合并按 atom 数、翻译按行数自动分批，程序校验响应并处理失败，缓存已完成部分。批次大小仍需结合模型的输出上限调整。

内容对了，SRT 也未必能直接用

早期需要从聊天窗口复制完整字幕，留意空行，并人工检查模型选择的合并结束时间；内容与格式问题缠在一起。

现在：LLM 不生成 SRT 时间码和排版，程序渲染最终文件。这避免模型重写时间轴，但 ASR 时间误差和成片阅读节奏仍需检查。

SIDE BY SIDE

同样是自动字幕，
优化的是不同环节。

以本地 GrillMaster 简体 fork 为具体对照，而不是给“主流项目”贴统一标签。两者都支持缓存与分块处理；区别在上下文输入和输出责任。

维度GrillMaster 多模态上下文maijev 职责拆分
识别与断句ElevenLabs Scribe v2 → 日文 SRT以生成的字幕为基础，进入翻译阶段。MAI 词级 ASR → atom → LLM 合并先按静音、标点和 speaker 边界拆分，再由模型决定语义合并关系。
翻译看什么字幕 + 音频 + 图片 + pre-pass 简报全片预处理和局部分块均使用多模态资料，帮助理解语气与画面。日文行 + 通用规则 + 可选词库翻译阶段只接收文本；画面信息先经外部 OCR 转成文字，再进入可选词库支线。
时间轴责任模型输出字幕，随后验证与修复校验分块 index / timecode，必要时调用额外模型修正结构。模型不生成 SRT 时间戳合并只返回分组，翻译只返回 id 与译文；程序从原始边界恢复时间轴。
跨批一致性共享丰富的全片简报人物对照、专有名词、固定梗、整体语气与局部摘要。共享 glossary.md一次纯文本 pre-pass 归并实体写法，每批翻译注入同一词库；也可人工覆盖。
处理与交付SRT / ASS 与可选后处理可选润色、封面、归档、字幕烧录，更接近完整观看交付链路。聚焦日文与中文 SRTCLI 或可选 Web GUI；保留分阶段缓存，可编辑词库后重翻。
需要接受的取舍更多上下文，也有更多媒体处理音视频输入、模型输出与修复环节需要一起管理。结构更受控，不等于语境更完整纯文本翻译无法直接听语气、看动作；视觉笑点与复杂漫才仍需要人工判断。
不是“全面替代”，而是不同取舍。

需要模型直接理解画面与语气，可以考虑多模态路线；更在意时间轴的责任边界、译名可控和重翻过程，maijev 提供了另一种组织方式。没有同素材、同模型的对照测试，不宣称哪一个翻译质量更高。

SMALLER CONTRACTS

让模型做判断，
不让它重抄整个字幕文件。

长视频里的格式风险，不只靠一句“请严格遵守格式”解决。maijev 把输出压缩为可校验的数据，再由程序组装成字幕。

合并阶段：只回答“哪些放一起”

输入带编号的 atom，模型返回分组。程序检查连续性、重复 id 和静音跨度，再取首尾 atom 的时间。

// 输入（简化示意）
0 | s1 | 今日は
1 | s1 | よろしくお願いします。

// 模型输出
{"groups": [[0, 1]]}

// 程序恢复
start = atom[0].start
end   = atom[1].end

断句边界可以重新组织，时间来源不变。

翻译阶段：只回答“这句怎么译”

模型接收 id 与日文行，返回对应译文。程序校验 id 覆盖情况，并将译文与已有时间边界对齐。

// 输入（简化示意）
0    今日はよろしくお願いします。

// 模型输出
{"lines": [{"id": 0, "zh": "今天请多关照"}]}

// 程序组装
原 start + 原 end + 中文译文
→ out_zh.srt

空译文回退原文，避免悄悄丢掉一句。

边界明确 ≠ 自动获得完美时间轴

时间准确度仍取决于 ASR 的词级时间戳和边界策略。这里解决的是 LLM 重写时间码的风险，不是消除识别本身的误差。

ONE VIDEO, ONE GLOSSARY

名字不要每批猜一遍。

同一个名字，可能有汉字、假名和识别变体。先在全片范围归并，再把同一份词库交给每个翻译批次。

* TVer / Abema 来源有数据时

Jev 做筛选，不做 OCRCLASSIFY

OCR 由外部工具完成。Jev 负责区分人名、节目名、地点 / 品牌与普通对白、效果字等；筛出的实体交给 pre-pass 归并，不把噪声直接铺进每批翻译。

少一层，也能继续跑OPTIONAL

没有 Jev 凭据，OCR 原文直接进 pre-pass；没有 OCR，可单独使用 --prepass 从全文生成词库。什么都不加也能翻译；检测到来源 cast 名单时会自动进行 pre-pass。

不对的名字，人来定EDITABLE

项目不内置特定节目词库。可注入外部术语表，或在 Web GUI 修改人工词库并“保存并重翻”。已完成的识别、合并和 pre-pass 可复用缓存。

BUILT FOR LONG VIDEOS

长视频，不必每次从头来。

识别、合并、词库与翻译分开落盘。失败能定位，调词库不用重跑识别，换模型也不会静默复用旧结果。

01 / TRANSCRIBE

长音频拆开识别

ffmpeg 提取音频，在静音附近切成约 5 分钟的片段。ASR chunk 独立缓存与重试，成功的部分无需重复请求。

02 / RESUME

缓存跟着内容走

合并、翻译和 pre-pass 的缓存考虑输入、提示词与模型。更改相应配置时，对应缓存自动失效。

03 / REVISE

把人工精力留给校对

生成日文和中文字幕后，集中检查人名、梗与视觉语境。自动化减少重复操作，不替代对成片的判断。

一个运行样本，不是性能承诺。

可以不使用命令行吗？

可以。安装 uv sync --extra gui，再运行 uv run python -m flows.maijev.gui，浏览器打开 http://127.0.0.1:8792。GUI 支持选文件、填远程来源、看阶段进度与日志、预览及下载字幕，以及编辑词库后重翻。服务本身没有账号鉴权，不要直接暴露公网。

它会完整理解视频里的画面吗？

不会。当前翻译与 pre-pass 都是纯文本调用；可选视觉支线提取的是 OCR 文字线索，不是把完整视频交给多模态模型。人物动作、音调和画面笑点可能缺失，这正是与 GrillMaster 路线的一个重要取舍。

还有哪些需要人工留意的地方？

ASR 仍可能识别错误，speaker 编号只保证单个 ASR 请求范围内有效，跨 chunk 不保证同一个人使用相同编号。共享词库帮助统一写法，但不保证每个名字都判断正确；漫才、双关、多人抢话和画面依赖内容仍需校对。当前项目聚焦 SRT，不包含 GrillMaster 的完整 ASS、烧录与归档链路。
